### How the current paths fit together

- `ZoneSimulation::advance_tick` in zone.rs orchestrates intents, movement/physics, timed swings and combat. combat.rs drives basic player swings and common damage; casting.rs/ability.rs drive ability use; the graph controls compatibility, follow-ups, interruption and authored movement where wired. Preserve these ownership boundaries; an action graph orchestrates phases/transitions, not the collision solver or all attack algorithms.
- `action::BASELINE` is the module-level constant in action/baseline.rs. `action_inspection` reads the real canonical state; the browser lab reads it through the local host and WASM. In the lab a validated alternate graph is zone setup, not a production save configuration. The promotion tool produces reviewed baseline source.
- The basic strike's weapon profile selects the variant and shape; zone state determines actual contact; projection/events drive both clients' shared clip/effect logic. `Fit` aligns a clip to a zone contact tick. Physical cover is still geometric; visual contact alignment alone does not prove a visually correct sweep or VFX.
- `MovementPredictor` uses another instance of the same ZoneSimulation and reconciles against projected state, not an independent movement algorithm. Combat and other units are absent from the predictor; assess the effect of any new restriction on correction, do not assume prediction already observes every combat state.

The task lookup does not connect the basic-strike, action-graph, movement, presentation and lab source/test paths as one combat capability; there is no combat-specific scope. In particular #380, #413, #414, #383 and #885/#892/#928 should be retrieved before work on combat timing. ## Remaining phase-1 work and handoff

The combat pilot and top-level map are complete as an initial slice. The wider inventory remains open: trace concrete callers, normal-runtime reachability and ownership in each noncombat domain, enumerate shared/native/browser copies of the same semantic decision (especially #1154), and distinguish a reachable fallback, test oracle or intentionally experimental implementation from an obsolete path. Read talent/progression code and existing product decisions more deeply before proposing trees. A local checkout is required for a complete repository-wide call graph, lints/build reachability and running Action Lab; the API-based review did not perform these checks.

Suggested first consolidation after that boundary is approved: make basic standing/running/jumping strike phases and their existing windows observable through the same graph, then compose lunge/momentum restrictions through one movement pipeline; test current behavior and tune the three moves individually in the existing lab. Preserve directed and arena behavior and canonical/replay semantics. Avoid widening this to ability redesign or rewriting weapon damage. For future changes, capability-specific lookup scopes can point at these code/test owners and exact Atlas sections using existing coding-tooling; no second metadata format is necessary.
