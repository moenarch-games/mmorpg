- **How to use this atlas**
  - This Atlas is the durable place for **what the product should be**. It has exactly **two semantic leaf-entry kinds: Decision and Question**. Navigation branches organize entries and are not a third kind. Existing leaves not explicitly marked `[question]` are Decisions.
  - A **Decision** is owner-selected product intent and remains in force until a later Decision supersedes it. A **Question** is a consequential unresolved choice. New Question leaves are marked `[question]`; an unanswered Question is not automatically a blocker.
  - Coding agents retrieve the relevant Atlas entries before making consequential product choices. Follow applicable Decisions. If an unanswered Question materially affects the current task, ask the owner **one question at a time**. If work exposes a new consequential fork, append a Question instead of choosing silently.
  - When a Question is answered, preserve it and append a Decision that says `Answers X.Y`. When intent changes, preserve the old Decision and append a Decision that says `Supersedes X.Y`. Do not introduce parallel semantic categories such as constraints, deferred decisions, assumptions, or principles; express those meanings in Decision/Question text and relationships.
  - Each bold dotted number identifies exactly one entry or navigation branch; for example, `1.3.2` is the runtime-partition Decision. References such as `see 1.3.3` refer to these IDs, not line numbers or automatically numbered Markdown lists.
  - This is historical and append-only by **stable IDs and owner intent**: new choices receive the next unused numeric child ID under their original numbered parent. Never renumber, remove, reuse, or silently rewrite an existing ID. An explicitly owner-approved navigation cleanup may change physical order **within that same numbered parent** while preserving every decision/question ID, kind, statement, references and history. Concurrent authors must reconcile numeric ID allocation.
  - **Topic:** labels inside long sections are **unnumbered navigation signposts**, not Decisions, Questions or new numbered parents. The dotted ID, not physical list position or signpost, determines an entry's owning parent. New Decisions use the next unused ID even when entries are visually grouped out of numeric order.
  - Bracketed implementation status on Decisions describes evidence **on 2026-10-11**, not another Atlas entry kind or live completion tracking. `implemented` means demonstrated in current code/docs; `implemented in reference` is explicitly not a production distributed deployment; `agreed design; pending` comes from existing open design issues.
  - Source links point to the inspected repository commit or issue. Existing ADRs/specifications remain authoritative for detailed contracts; issues own work, code/tests own implementation evidence, and this Atlas owns durable product intent and unresolved product Questions.

    - **2.1.6** [decision] MMORPG's authoritative zone physics is **Rapier**, as in ARPG (ARPG Atlas 2.3.1/2.3.2): full 3D `rapier3d` (f32) with default features, embedded in the Rust zone simulation shared by native hosts and the WASM local host. Players and creatures move with Rapier's `KinematicCharacterController` on capsule colliders; f32 positions and velocities are authoritative and rounded only for network projections (gameplay rules read a whole-unit view). Canonical snapshots keep the exact f32 unit state and recovery rebuilds the physics world, never saving Rapier internals. `physics_engine::World` was removed with no shim; gameplay outcomes stay in `mmorpg-core`, and each concrete Rapier gap feeds back into physics-engine issues. Supersedes 2.1.4. (Owner, live session 2026-10-18; [#271](https://github.com/moritzbrantner/mmorpg/issues/271), supersedes #46, #55 and #165)
    - **2.1.7** [decision; implemented] Refines 2.1.6 for evidence only: a **test/bench-only A/B seam** lets the same zone simulation run on physics-engine's `approximate::World` so it can be compared with Rapier on MMORPG's workloads. `physics::World` is a backend enum (`physics/rapier.rs`, `physics/engine.rs`) selected at runtime only under the non-default `physics-ab` cargo feature; production and WASM builds never compile physics-engine, and Rapier remains the sole authority. Debris stays on Rapier in both arms. A merge-blocking invariant A/B test over existing deterministic drivers runs with the feature in the existing CI job; timing is a manual example. No production backend switch is implied. ([docs](../PHYSICS_AB.md); [physics-engine #330](https://github.com/moritzbrantner/physics-engine/issues/330), owner decisions 2026-10-19)
